1 · The Locked Spec (what we are building)

Cognitive job: Give Instant Mechanic's operations team one screen that answers “what is happening right now, and what needs a human?” across vehicle-service bookings, mechanics, customers and revenue — and let an operator request/dispatch a mechanic against a booking. This is a monitoring and dispatch surface over operational data, not a customer-facing product and not an automation.

Inputs: Operational Postgres (Supabase): bookings, mechanics, customers, payments. Operator filters (date range, status, region). Operator dispatch actions.  →  Outputs: Dashboard views (booking queue, mechanic availability & load, customer records, revenue rollups) + assignment writes back to bookings + an audit row per operator action.

Autonomy level: Level 1 — assistive. The system computes and displays; it never changes booking state on its own.  |  Human-in-the-loop points: Every write. Requesting/assigning a mechanic, cancelling, and any refund or price override are explicit operator clicks with confirmation.

Failure tolerance: Reads: degrade visibly — a failed panel shows an error state and a data-as-of timestamp, never a blank panel and never a silently stale number. Revenue is never approximated. Writes: zero tolerance for duplicates — a double-clicked dispatch must assign once (idempotent on booking+mechanic).  |  Trust boundary: Internal staff only, authenticated; no anonymous access. Behind the login sits customer PII (name, address, phone, vehicle) and revenue data, so authn is a hard gate and ops-vs-admin role separation governs refunds and exports. The database is hosted Supabase reached over the public internet — the connection string is a secret and the DB is not on a private network.

Filled during Genesis step G0 (Cognitive Design) via agentic-swe-master.

2 · Definition of Done (binary gates — checked by the VERIFIER, not the maker)

Dependency direction inward, zero cycles (modular-architecture gate)
Every outbound call has a timeout / circuit-breaker (production-readiness gate)
Booking lifecycle drawn as an explicit state machine; every status transition is enumerated and validated (P3 Backend gate)
Every operator write is idempotent — retrying it has no side effect it didn't have on first execution (P12 Reliability gate)
Prisma schema changes are backward-compatible for at least one full deployment cycle (P14 Data gate)
Threat model written with specific adversary categories (unauthenticated internet, ex-staff with a stale session, over-scoped ops account) (P11 Security gate)
RBAC implemented — ops vs admin; refunds/exports are admin-only and enforced server-side, not just hidden in the UI (P11 Security gate)
Audit trail is append-only: every dispatch/cancel/refund writes an immutable row with actor, target and timestamp (P11 Security + P15 Governance gate)
No customer PII in logs or error payloads (P11 Security gate)
HITL touchpoints mapped — no dashboard control mutates booking state without an explicit confirm (P2 Frontend gate)
(cd backend && npx tsc --noEmit) && (cd frontend && npx tsc --noEmit) clean AND cd backend && node --test green in CI
One verify pass by a separate agent/model (L4)
No context-graph.json invariant violated by the change
